## Етап 1. Іменники й дієслова

**Іменники** (усі з брифу):
місто, станція (прокату), велосипед, номер, звичайний велосипед, електричний велосипед, клієнт, ім'я, баланс, рахунок, хвилина, кількість хвилин, гроші, гривня, адміністратор, мережа

**Дієслова** (усі з брифу):
стоять (на станції), буває (звичайний/електричний), має (ім'я, баланс, номер), взяти (велосипед), покататись, повернути (велосипед), коштує, списуються (гроші), бачити (скільки велосипедів), заробила (мережа)

**Рішення щодо іменників:**

| Іменник | Клас / атрибут / не потрібен | Чому |
|---|---|---|
| станція | клас `Station` | має назву і велосипеди |
| велосипед | клас `Bike` | має номер і тип |
| клієнт | клас `Client` | має ім'я і баланс |
| номер | атрибут `Bike` | це просто число велосипеда |
| звичайний / електричний | атрибут `Bike` | це тип велосипеда |
| ім'я | атрибут `Client` | належить клієнту |
| баланс, рахунок | атрибут `Client` | це гроші клієнта |
| хвилина | число у функції | потрібна тільки для підрахунку ціни |
| гроші, гривня | ціна в `Payment` | потрібні тільки для підрахунку ціни |
| мережа | виручка в `Payment` | від неї треба тільки суму грошей |
| адміністратор | не потрібен | він тільки дивиться звіт |
| місто | не потрібен | ні на що не впливає |

**Рішення щодо дієслів:**

| Дієслово | Кому належить (клас або окрема функція) |
|---|---|
| стоять | `Station` (`add_bike`, `count`) |
| буває | `Bike` (атрибут `bike_type`) |
| має | не дія, це атрибути |
| взяти | `Rental.rent_bike()` |
| покататись | число хвилин у `Rental.return_bike()` |
| повернути | `Rental.return_bike()` |
| коштує | `Payment.calc_cost()` |
| списуються | `Client.charge()` |
| бачити | звіт у `main()` |
| заробила | `Payment.get_total_revenue()` |

## Етап 2. Картки класів

### Клас: Bike

| Що він ЗНАЄ (атрибути) | Що він ВМІЄ (методи) |
|---|---|
| number — номер | is_electric() — повертає True, якщо електричний |
| bike_type — "regular" або "electric" |  |

### Клас: Station

| Що він ЗНАЄ (атрибути) | Що він ВМІЄ (методи) |
|---|---|
| name — назва | add_bike(bike) — ставить велосипед на станцію |
| bikes — список велосипедів | take_bike() — повертає велосипед або None, якщо пусто |
|  | has_bikes() — повертає True, якщо є вільний велосипед |
|  | count() — повертає кількість велосипедів |

### Клас: Client

| Що він ЗНАЄ (атрибути) | Що він ВМІЄ (методи) |
|---|---|
| name — ім'я | top_up(amount) — поповнює баланс |
| balance — баланс у грн | can_pay(amount) — повертає True, якщо грошей вистачає |
| current_bike — велосипед, на якому катається | charge(amount) — списує гроші |

### Клас: Rental

| Що він ЗНАЄ (атрибути) | Що він ВМІЄ (методи) |
|---|---|
| payment — об'єкт Payment | rent_bike(client, station) — повертає (True, bike) або (False, "no_bikes") / (False, "already_riding") |
|  | return_bike(client, station, minutes) — повертає (True, cost) або (False, "no_bike") |

### Клас: Payment

| Що він ЗНАЄ (атрибути) | Що він ВМІЄ (методи) |
|---|---|
| total_revenue — загальна виручка | calc_cost(bike, minutes) — повертає ціну (2 або 5 грн/хв × хвилини) |
|  | pay(client, bike, minutes) — списує гроші з клієнта, додає у виручку, повертає ціну |
|  | get_total_revenue() — повертає загальну виручку |

Сценарій «Оля бере електричний велосипед на станції А, катається 20 хвилин і повертає його на станцію Б»:

| Крок сценарію | Хто відповідає (клас.метод або функція) |
|---|---|
| Оля бере велосипед на станції А | Rental.rent_bike(olya, station_a) |
| Перевірити, що на станції є велосипед | Station.has_bikes() |
| Забрати велосипед зі станції А | Station.take_bike() |
| Оля катається 20 хвилин | число 20 передається в return_bike() |
| Оля повертає велосипед на станцію Б | Rental.return_bike(olya, station_b, 20) |
| Поставити велосипед на станцію Б | Station.add_bike() |
| Порахувати ціну: 20 × 5 = 100 грн | Payment.calc_cost() |
| Списати 100 грн з балансу Олі | Payment.pay() → Client.charge(100) |
| Додати 100 грн у виручку мережі | Payment.pay() оновлює total_revenue |

## Етап 3. План main() і файли

**Демо-сценарій по кроках:**

1. Створити 2 станції: А і Б.
2. Створити 5 велосипедів (3 звичайні, 2 електричні) і поставити їх на станції.
3. Створити 2 клієнтів з різним балансом: Оля (300 грн) і Петро (150 грн).
4. Оля бере електричний велосипед на станції А.
5. Через 20 хвилин повертає його на станцію Б.
6. Програма рахує вартість: 20 × 5 = 100 грн.
7. З балансу Олі списуються 100 грн.
8. Петро робить ще дві поїздки.
9. Спроба взяти велосипед на порожній станції — програма виводить зрозуміле повідомлення.
10. Вивести баланси клієнтів, кількість велосипедів на станціях та загальну виручку.
11. Перевірки через assert.

**Файли і власники:**

## Презентація

### Вивід програми

```
Оля бере велосипед на станції А: OK (велосипед №2 (electric))
Оля повертає велосипед на станцію Б, грн: OK (100)
Петро бере велосипед на станції Б: OK (велосипед №2 (electric))
Петро повертає велосипед на станцію А, грн: OK (75)
Петро бере велосипед на станції Б: OK (велосипед №5 (electric))
Петро повертає велосипед на станцію А, грн: OK (50)
Оля бере велосипед на станції Б: ПОМИЛКА — на станції немає вільних велосипедів
Оля бере велосипед на станції В: ПОМИЛКА — на станції немає вільних велосипедів
=== Баланси ===
Оля: 200 грн
Петро: 25 грн
=== Звіт адміністратора ===
Станція А: 6 велосипедів
Станція Б: 0 велосипедів
Станція В: 1 велосипедів
Розряджені електровелосипеди:
  №6 на станції А: 10%
  №7 на станції В: 15%
Загальна виручка: 225 грн
Усі перевірки пройдено
```

### Блок 1. Архітектура
- Які у нас класи: Bike (велосипед), Station (станція), Client (клієнт), Rental (поїздка: взяти / повернути), Payment (вартість і виручка).
- Файли і власники:
  - bikes.py: Bike, Station (Володимир)
  - clients.py: Client (Гліб)
  - rentals.py: Rental (Матвій)
  - payments.py: Payment (Вадим)
  - main.py: main(), тестові дані, звіт, assert (Роман)

### Блок 2. Демо
- Помилкова дія і реакція програми: Оля намагається взяти велосипед на станції Б, де вже немає велосипедів. Програма не падає, а виводить зрозуміле повідомлення: «на станції немає вільних велосипедів». Так само для станції В, де стоїть лише розряджений велосипед: «є лише розряджені велосипеди (заряд нижче 20%)».
- Звіт адміністратора: станція А: 6 велосипедів, Б: 0, В: 1. Розряджені електровелосипеди: №6 на станції А (10%) і №7 на станції В (15%). Загальна виручка мережі: 225 грн (100 + 75 + 50).

### Блок 3. Нова вимога
- Скільки файлів і функцій/методів змінили: нова вимога стосувалась заряду електровелосипедів. Змінили 2 файли (bikes.py і main.py), приблизно 8 місць:
  - bikes.py: Bike.__init__ (атрибут battery), Bike.is_low_battery (новий), Station.take_bike, Station.has_bikes, Station.low_battery_bikes (новий);
  - main.py: словник REASONS, main(), report().
  Файли clients.py і payments.py не змінювались.
- Що допомогло або завадило: допомогло, що кожен клас відповідає за своє. Логіка вибору придатного велосипеда сховалась усередині Station, тому Rental майже не довелось чіпати, а Payment і Client взагалі не знають про заряд. Завадило те, що розряджені велосипеди довелося враховувати одразу в кількох методах Station (take_bike, has_bikes), і їх треба було змінювати синхронно.

### Блок 4. Мікросервіс
- Що винесли б в окремий мікросервіс: Payment. Він майже незалежний: має лише тарифи і загальну виручку, а решту отримує через виклики (is_electric у велосипеда, charge у клієнта).
- Що від цього стало б складніше:
  - зараз pay() напряму викликає client.charge(), а з мікросервісом це перетворилось би на мережевий запит, який може не пройти;
  - з'явився б ризик, що гроші списались, а виручка не записалась (або навпаки);
  - довелося б синхронізувати дані про клієнтів і велосипеди між службами та налаштовувати окреме розгортання.
